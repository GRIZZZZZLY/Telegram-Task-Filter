# Аудит: TG Focus Filter — готовность к командному использованию

**Дата:** 2026-02-28 (обновлено: 2026-02-28 v2)  
**Цель:** Превратить личный инструмент в командный — любой участник команды должен уметь установить и настроить приложение без правки кода.  
**Модель использования:** Каждый коллега ставит приложение **локально на свой ПК** и авторизуется своим Telegram-аккаунтом. Общий сервер не нужен — полная изоляция по умолчанию.  
**Успех:** Новый пользователь вводит свой Telegram handle в Settings → задачи создаются при упоминании в мониторируемых чатах.

---

## 🔴 КРИТИЧНО (блокирует командное использование)

### 1. Хардкод `@igo_kravts` в `default_rules.yaml`
**Файл:** `shared/rules/default_rules.yaml`, строка 23  
**Проблема:** Правило `mention: "@igo_kravts"` — задачи создаются только при упоминании конкретного человека. Новый пользователь должен вручную редактировать YAML-файл внутри пакета.  
**Решение:** Убрать `mention` из дефолтного правила — listener уже фильтрует по `filter_strict_mentions=True` + `tg_mention_handles` из Settings. Правило в YAML нужно только для приоритизации по ключевым словам.

```yaml
# Было:
when:
  mention: "@igo_kravts"

# Должно быть:
when: {}   # match everything that passes listener filters
```

**Оценка:** 15 минут.

---

### 2. Нет UI для редактирования mention handles
**Файл:** `config.py` — `tg_mention_handle` / `tg_mention_handles`  
**Проблема:** Поле есть в Settings API, но в SettingsScreen нет поля ввода для handle. Пользователь не знает, что нужно настроить.  
**Решение:** Добавить текстовое поле «Мой Telegram handle» в SettingsScreen (рядом с чатами).

**Оценка:** 30 минут.

---

### 3. Нет уведомления в UI при сбое commit (реакции)
**Файл:** `commit_worker.py`, строка 157–166  
**Проблема:** Если Telegram вернул ошибку при отправке реакции — ошибка пишется только в лог. Задача остаётся в `done` без реакции. Пользователь не знает.  
**Решение:** При `EventType.error` — WebSocket broadcast `"task_commit_failed"` → UI показывает toast/badge на задаче.

**Оценка:** 1–2 часа.

## 🔴 КРИТИЧНО — новые задачи (добавлено v2)

### N1. Приоритет: все задачи приходят как HIGH — нужен "Normal" (серый, дефолт)
**Файлы:** `shared/rules/default_rules.yaml`, `models.py`, `TaskCard.tsx`, `task.ts`  
**Проблема:** Правило в YAML задаёт `priority: high` → все задачи красные. ORM-дефолт `medium`, но YAML перебивает его. Уровня "Normal" (серого) нет.  
**Решение:** Добавить новое значение `normal` в `TaskPriority` (Python enum + frontend тип). Сделать `normal` дефолтом в правиле и ORM. Цикл смены приоритета: `normal → high → medium → low → normal`.

**Затронутые файлы:**
- `services/api/app/models.py` — добавить `normal = "normal"`, поменять дефолт
- `shared/rules/default_rules.yaml` — `priority: normal`
- `src/types/task.ts` — добавить `'normal'` в `TaskPriority`
- `src/components/tasks/TaskCard.tsx` — добавить в `PRIORITY_CONFIG` и `PRIORITY_CYCLE`

> **Важно про SQLite:** SQLAlchemy хранит Enum как VARCHAR без CHECK-констрейнта → добавление `normal` не требует миграции БД. Старые записи `high/medium/low` остаются валидными.

**Дизайн:**
```
normal → серый:   bar: bg-slate-500, badge: text-slate-400, badgeBg: bg-slate-500/10
```

**Оценка:** 30 минут.

---

### N2. Тело задачи не отображается — нет кнопки "Развернуть"
**Файлы:** `task.ts`, `TaskCard.tsx`  
**Проблема:**
- Backend корректно сохраняет полный текст сообщения в `task.body` (когда текст длиннее title)  
- Но `Task` тип во frontend **не содержит поля `body`** → оно теряется при десериализации  
- В `TaskCard.tsx` тело никогда не рендерится, кнопки "Развернуть" нет  
- Title ограничен `line-clamp-2` (≈2 строки), длинные сообщения обрезаются без возможности прочитать

**Решение:**
1. Добавить `body?: string | null` в `Task` тип (`task.ts`)
2. В `TaskCard.tsx` добавить состояние `expanded: boolean`
3. Показывать кнопку «Развернуть» когда `task.body` непустое
4. При развёрнутом состоянии: title без `line-clamp`, + блок с `task.body`
5. Кнопка «Свернуть» для возврата

**Дизайн кнопки:** маленький текст-link под title, `chevron-down/up` + "Развернуть" / "Свернуть"

**Оценка:** 45 минут.

## 🟠 ВАЖНО (ухудшает UX при командном использовании)

### 4. Шумный лог: каждое сообщение без упоминания логируется на INFO
**Файл:** `tg_listener.py`, строка 130–133  
**Проблема:** `logger.info("MSG | chat=%s sender=%s mentions=%s text=%.80r", ...)` — в активных чатах это сотни строк в минуту. Лог-вьювер в UI становится бесполезным.  
**Решение:** Понизить до `logger.debug`. Оставить INFO только для сообщений, которые прошли все фильтры.

**Оценка:** 5 минут.

---

### 5. Нет поиска по задачам в UI
**Файл:** `TaskList.tsx`, `tasks.py` (backend поддерживает фильтры, но не текстовый поиск)  
**Проблема:** При 50+ задачах невозможно найти нужную.  
**Решение:** Строка поиска в TopBar → фильтрует локально по `task.title + task.body`.

**Оценка:** 1 час.

---

### 6. Нет фильтрации по чату в UI
**Файл:** `TaskList.tsx`  
**Проблема:** Все задачи из всех чатов в одном списке. При мониторинге 5+ чатов — каша.  
**Решение:** Dropdown «Все чаты / Чат X» в TopBar → передаёт `chat_id` в `GET /tasks`.

**Оценка:** 2 часа.

---

### 7. Нет пагинации в UI (frontend всегда берёт первые 50)
**Файл:** `useTasks.ts` — `limit=50` хардкод  
**Проблема:** Backend поддерживает `limit/offset`, но UI никогда не запрашивает следующую страницу.  
**Решение:** Кнопка «Загрузить ещё» или infinite scroll.

**Оценка:** 1 час.

---

### 8. Нет подтверждения при dismiss
**Файл:** `TaskCard.tsx` — кнопка dismiss  
**Проблема:** Задача удаляется мгновенно без возможности отмены (в отличие от Done, у которого есть undo-окно).  
**Решение:** Добавить inline-undo для dismiss (аналогично Done), или хотя бы `confirm()`.

**Оценка:** 30 минут.

---

### 9. Catchup worker: потенциальная проблема с thread_id фильтром
**Файл:** `catchup_worker.py`, строка 133  
```python
if monitored_thread_ids and thread_id not in monitored_thread_ids:
```
**Проблема:** `thread_id` — это `int | None`, `monitored_thread_ids` — `list[int]`. Если `thread_id=None` и список непустой — сообщение пропускается (корректно). Но если `thread_id` пришёл как строка из другого источника — сравнение провалится тихо. Это зеркало live listener (строка 108), там та же логика.  
**Решение:** Явное приведение типов при сравнении.

**Оценка:** 10 минут.

## 🟡 ЖЕЛАТЕЛЬНО (улучшает командный опыт)

### 10. Нет retry при сбое отправки реакции
**Файл:** `commit_worker.py`  
**Проблема:** Telegram API может вернуть временную ошибку (flood wait, network). Сейчас — тихий сбой.  
**Решение:** Экспоненциальный retry 3 раза с задержкой, затем `EventType.error`.

**Оценка:** 1 час.

---

### 11. Нет экспорта задач
**Проблема:** Нет способа выгрузить задачи в CSV/JSON для отчёта.  
**Решение:** `GET /tasks/export?format=csv` + кнопка в UI.

**Оценка:** 2 часа.

---

### 12. Нет массовых операций
**Проблема:** Нельзя выбрать несколько задач и выполнить их одним действием.  
**Решение:** Checkbox-режим + «Выполнить выбранные».

**Оценка:** 3 часа.

---

### 13. Нет статистики
**Проблема:** Нет понимания нагрузки: сколько задач в день, из каких чатов, среднее время выполнения.  
**Решение:** Простой дашборд на основе `Event` таблицы.

**Оценка:** 4 часа.

## Вне скоупа (Parking Lot)

- Мультипользовательность на одном сервере (несколько аккаунтов в одном процессе) — не нужно, у каждого своя установка
- OR-логика в правилах YAML
- Регулярные выражения в правилах
- Фильтрация по sender в правилах
- Дашборд статистики
- Массовые операции (checkbox-режим)
- Мобильное приложение
